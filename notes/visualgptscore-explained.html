A 4-minute explanation · Proposed experiment, no new results

Can it recognize the SVG
it cannot write?

Writing an entire SVG tests several abilities at once: seeing the image, representing its content in code, maintaining syntax, and finishing the sequence. A broken output does not tell us which ability failed.

1. What is VisualGPTScore?

Give the model an image and a candidate description. Instead of asking it to generate an answer, ask: how probable is this exact description given the image? We propose using SVG code as that description.

P(S | I) = ∏ P(sₜ | I, prompt, s₁ … sₜ₋₁)
log P(S | I) = Σ log P(sₜ | I, prompt, s₁ … sₜ₋₁)

I is the image; S is the supplied SVG, split into tokens. At every position, we read the probability assigned to the actual next candidate token. We supply the preceding candidate tokens, even if the model would have generated something else. This is teacher forcing; no weights are updated.

Toy calculation: three tokens, not a real SVG

Candidate A: probabilities 0.8 × 0.5 × 0.9 = 0.36
Candidate B: probabilities 0.8 × 0.2 × 0.9 = 0.144

Log scores: A = −1.02; B = −1.94. Higher / less negative wins. This is model likelihood, not a calibrated probability that A is correct.

The original likelihood idea uses a sum of log probabilities. Longer strings tend to have smaller probabilities. For our SVG probe, we would freeze a length rule in advance: prefer equal-token-length pairs and report mean log probability per SVG token. That normalization is our scoring choice, not a new claim about the original metric. Prompt and image tokens are not scored.

3. Why must the preference reverse?

A model might always prefer A because its code is more familiar. Correctly choosing A once is therefore weak evidence. Show it both images, retaining exactly the same two candidates: an image-sensitive model should prefer A for the left image and B for the right image.

Input: left circle

Image-sensitive example: A −0.20 · B −0.80 → A wins
Image-ignoring example: A −0.30 · B −0.60 → A wins

Illustrative mean log scores only. Click to see why one correct choice is insufficient.

Our proposed margin adds the two matching preferences:

G = [score(A | left) − score(B | left)]
　+ [score(B | right) − score(A | right)]

The image-sensitive example gives 0.60 + 0.60 = 1.20. The image-ignoring example gives 0.30 − 0.30 = 0. An image-independent code preference cancels.

Report the fraction of pairs where both choices are correct, plus G and uncertainty across source diagrams. Positive G alone is insufficient: preference can move toward the right answer without actually reversing. Both-correct random guessing is 25% only under independent fair choices; use actual blind controls too.

4. What would it tell us across SFT?

  • Grounded discrimination: can the model distinguish matching from mismatching SVG content when valid candidates are supplied?
  • Output execution: can it generate a complete, renderable SVG on its own? This says nothing by itself about fidelity.

If the base already discriminates well, but only SFT improves execution, the measured matching ability predates our SFT. If discrimination improves too, SFT changes grounded task performance as well. If both remain poor, we have not demonstrated hidden competence.

This removes the need to generate syntax; it does not remove the need to understand SVG. Recognition with a supplied answer is easier than reconstruction. The probe measures specific edited properties, not all visual ability, and cannot identify which pretraining data caused them.

5. Is the companion diagnostic worth doing?

It scores one gold SVG with its correct image and a shuffled image. If the correct image lowers loss, the image helps predict that target. However, style alone could help; the supplied SVG prefix also reveals content. So it is a useful sanity check, but weak evidence of spatial understanding. I would make the controlled counterfactual probe the main addition and keep this optional.
